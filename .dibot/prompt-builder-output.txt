Crea FocusFlow, una app móvil consumer de enfoque diario para personas que trabajan o estudian y necesitan convertir una intención en una sesión concreta. El objetivo es que, al abrirla, el usuario elija o vea una tarea principal, inicie un bloque de concentración de 25 minutos, gestione una lista breve de tareas y entienda su progreso del día sin fricción. La experiencia debe sentirse publicable, rápida, calmada y funcional; evita features de productividad innecesarias.

## DIRECCIÓN VISUAL

Usa una sola dirección original: **“papel cálido + tinta carbón + lima de energía”**. Fondo marfil cálido (#F6F3EC), superficies blancas ligeramente cálidas, texto carbón, líneas gris piedra y un único acento lima/verde eléctrico para progreso, foco y acciones positivas. El contraste debe ser accesible, sobrio y optimista, no neón. Usa una sans geométrica muy legible para UI y números, con una serif editorial discreta solo para el saludo o una frase de intención. Define tokens semánticos para background, surface, elevated, text, muted, primary, accent, success, warning, danger, spacing y radius.

Antes de diseñar o programar, **abre y analiza todas las imágenes de `references/mobbin/` y lee `references/mobbin/README.md`**. Extrae de ellas la mayor cantidad posible de decisiones sobre color, contraste, tipografía, escala, espaciado, radios, elevación, navegación, cards, filtros, estados y movimiento, pero abstrae el lenguaje: no copies literalmente ninguna pantalla, marca, logo, texto, asset o composición. Usa las referencias de Opal/Mindvalley para la lectura del progreso, Life Reset para la concentración del timer, Granola para controles táctiles y Gemini para la jerarquía de tareas.

## FLUJO VERTICAL COMPLETO

Construye primero para 390 px, con soporte real para 375–430 px, safe areas y controles táctiles de 44–56 px.

1. **Hoy / home**: header con “Buenos días, [nombre opcional]”, fecha y avatar/menú mínimo. Hero “Tu foco de hoy” con una sola tarea principal, checkbox grande, prioridad y CTA “Enfocarme 25 min”. Si no existe tarea principal, muestra un empty state útil con “Elige una tarea para empezar” y CTA para crearla. Debajo, tarjeta del temporizador con estado “Listo para empezar”, progreso circular o anillo lineal y duración 25:00. Después, “Tareas de hoy” con lista breve, checkbox, título, etiqueta opcional y eliminar mediante swipe o menú; CTA “Añadir tarea”. Cierra con “Progreso del día”: sesiones completadas, minutos enfocados y barra de avance.
2. **Crear tarea**: sheet o pantalla modal con formulario React Hook Form + Zod: título requerido, descripción opcional, selector de “hacer principal” y duración sugerida bloqueada a 25 minutos en MVP. Botón “Guardar tarea”, cancelar y teclado usable. Al guardar, volver a Hoy y actualizar el cache.
3. **Temporizador activo**: pantalla inmersiva propia, sin fotografía. Timer grande 25:00, nombre de tarea, indicador de sesión, pausa/reanudar y “Terminar sesión”. Usa Motion con animación sutil del progreso, no decorativa. Confirmar antes de abandonar una sesión activa. Al llegar a 00:00, mostrar estado success con celebración contenida, minutos ganados y CTA “Marcar tarea completada” / “Volver a Hoy”.
4. **Editar/completar/eliminar**: completar actualiza tarea y progreso de inmediato; editar reabre el formulario; eliminar pide confirmación y permite undo breve. Las tareas completadas quedan visibles en filtro Completed o bajo una sección colapsable.
5. **Historial/progreso**: accesible desde una navegación inferior “Hoy” y “Progreso”. Mostrar resumen de hoy, sesiones recientes y una racha simple, con estados empty para una cuenta nueva. No conviertas esto en un dashboard complejo.

## INTERACCIONES Y ESTADOS

Implementa loading skeleton para home/lista/progreso, submitting disabled con spinner en guardar, optimistic update seguro para completar, error de red con retry, error de validación inline, empty states para cero tareas/cero sesiones, populated state, confirmación de eliminar, success toast/banner al crear o completar, y estado offline comprensible si falla la API. El timer debe ser robusto ante pausa, background y retorno a la app: persiste start/end/pausedAt localmente y recalcula el tiempo restante, sin perder la sesión. Usa feedback haptics/visual solo si la plataforma lo permite y siempre con fallback.

## NAVEGACIÓN Y RESPONSIVE

Usa React Router con dos rutas principales: `/` Hoy y `/progress` Progreso; modal/sheet para crear/editar y ruta o vista dedicada para `/focus`. Bottom navigation fija con dos destinos, respetando safe-area-inset-bottom. Mantén el CTA primario visible, evita scroll horizontal y comprueba que el teclado no tape inputs. A 390 px debe verse una pantalla equilibrada; en anchos mayores limita el contenido a una columna de lectura cómoda sin cambiar la jerarquía.

## COMPONENTES Y STACK

Conserva el stack Dibot existente: React + Vite + TypeScript + Bun + Tailwind, Base UI, Motion, Embla solo si realmente aporta, Phosphor Icons, React Router, Zustand, TanStack Query, React Hook Form, Zod, Drizzle ORM, `@libsql/client` y Turso/libSQL. No agregues otra UI framework ni reemplaces la arquitectura. Crea componentes pequeños y reutilizables: AppShell, BottomNav, TodayHeader, FocusTaskCard, TimerCard, FocusTimer, TaskList, TaskRow, TaskForm, ProgressSummary, EmptyState, ConfirmDialog y Toast. Usa iconografía Phosphor consistente, labels accesibles, focus states y aria-labels.

## API Y DATOS

Usa TanStack Query para todo dato remoto y Zustand solo para estado local efímero del timer, preferencias mínimas y UI. Como hay persistencia real, usa Drizzle + Turso/libSQL server-side. Todo acceso a base de datos vive en `api/`; nunca expongas `TURSO_AUTH_TOKEN`, `TURSO_PLATFORM_API_TOKEN` ni secretos con `VITE_`. Define en `api/db/schema.ts` tablas para `tasks` (id, title, description, isPrimary, completedAt, createdAt, updatedAt), `focus_sessions` (id, taskId, startedAt, endedAt, durationSeconds, status) y, si hace falta, una tabla mínima de preferencias. Añade endpoints server-side para listar tareas del día, crear, actualizar/completar y eliminar tareas, iniciar/finalizar sesiones y obtener el resumen de progreso. Valida payloads con Zod también en servidor, maneja errores y fechas en UTC, y actualiza/invalida queries tras mutaciones. Revisa las variables Turso según el contrato existente y, después de definir el schema, usa `bun run db:push` para sincronizar la base; no uses una base existente sin verificar su `TURSO_DATABASE_ID`.

## IMAGE PLAN

No uses fotografía ni ilustraciones reales en el MVP: la dirección “papel cálido + tinta + lima” funciona mejor con superficies, formas y Motion, mantiene el producto ligero y evita assets de terceros. Si el diseño necesita un fallback futuro para una ilustración de empty state, usa una ilustración geométrica generada en CSS/SVG local, no Mobbin ni marcas. No descargues ni reutilices assets de Mobbin, marcas o apps de terceros.

## CRITERIOS DE ACEPTACIÓN

- Un usuario puede crear, editar, completar y eliminar tareas, con persistencia real en Turso.
- Puede seleccionar una tarea principal y empezar/pausar/reanudar/terminar un timer de 25 minutos sin perder estado al cambiar de vista o volver de background.
- Hoy muestra siempre la tarea principal, lista breve, sesiones y progreso actualizado.
- Progreso muestra datos reales y estados empty/loading/error.
- Todas las mutaciones tienen feedback visual y manejo de errores; formularios validan correctamente.
- La UI funciona y se siente intencional a 390 px, con navegación, safe areas, accesibilidad básica y controles táctiles adecuados.
- Abre y estudia las seis referencias locales antes de diseñar; extrae decisiones visuales sin clonar.
- Conserva la arquitectura Dibot y no introduce dependencias UI innecesarias.

Valida tipos, rutas, interacción principal y responsive. Ejecuta `bun run build` como verificación final y corrige los errores de integración que aparezcan. No cierres una feature con mocks cuando deba usar API/Turso.

## REGLA DE VELOCIDAD

Trabaja con una dirección, un vertical slice y decisiones concretas. No hagas brainstorming, no presentes un plan largo y no abras direcciones visuales alternativas: implementa pronto la experiencia Hoy → tarea → foco → progreso.

Usa las referencias de Mobbin para extraer el lenguaje visual, no para copiar pantallas o assets; crea una implementación original. Empieza a programar ahora.

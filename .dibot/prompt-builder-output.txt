PRODUCTO, USUARIOS Y OBJETIVO
Construye FocusFlow, una app móvil de enfoque diario para personas que trabajan o estudian y necesitan convertir un día abrumador en una siguiente acción clara. La pantalla principal “Hoy” debe mostrar una tarea principal, un temporizador Pomodoro de 25 minutos, una lista breve de tareas y el progreso del día. Permite crear, completar y eliminar tareas, con persistencia real en Turso. Prioriza un vertical slice funcional, publicable y rápido de entender.

DIRECCIÓN VISUAL ÚNICA
Usa una dirección original llamada “papel cálido + tinta carbón + lima eléctrica de energía”: fondo marfil cálido (#F7F4EC), superficies blancas, texto carbón, verde lima como acción/progreso y coral sobrio solo para errores o borrar. Contraste AA, bordes finos, cards de radio 18 px, botones de 52 px, sombras difusas muy bajas y tipografía sans legible con números tabulares para el timer. La pantalla debe sentirse serena, editorial y táctil, no como un clon de ninguna app. Usa progresos lineales/circulares simples, microanimaciones de entrada y transición suave al completar; evita gradientes decorativos, exceso de color, ilustraciones y gamificación ruidosa.

REFERENCIAS VISUALES OBLIGATORIAS
Antes de diseñar o programar, abre y analiza **todas** las imágenes de `references/mobbin/` y lee su `README.md`. Extrae la mayor cantidad posible de decisiones: color, contraste, tipografía, escala, espaciado, radios, elevación, navegación, cards, filtros, estados y movimiento. Usa esos hallazgos para tomar decisiones, pero no copies literalmente pantallas, textos, logos, marcas, assets ni layouts. Las referencias son composición y lenguaje visual, no una fuente de assets.

PANTALLAS Y FLUJO VERTICAL COMPLETO
1. **Hoy (inicio):** safe area, saludo y fecha, indicador “X de Y completadas”, card destacada de tarea principal con checkbox y botón “Iniciar 25:00”, progreso del día, lista de 3–5 tareas con completar/eliminar y FAB o CTA “Nueva tarea”. Si no hay tareas, muestra empty state útil con “Crea tu primera tarea”.
2. **Nueva tarea:** bottom sheet o pantalla modal con input de título obligatorio, selector opcional “Hacer principal”, prioridad/etiqueta simple, cancelar y guardar. Enfoca el teclado, valida título vacío y confirma success con toast o feedback inline.
3. **Sesión de enfoque:** pantalla inmersiva con nombre de tarea, contador 25:00 grande, progreso circular o lineal, pausa/reanudar, cancelar y “Completar tarea”. Al llegar a cero muestra success, celebra con discreción y permite volver a Hoy.
4. **Detalle/acciones de tarea:** menú contextual o sheet para marcar completa/incompleta y eliminar con confirmación. No ocultes acciones esenciales.
5. **Resumen del día:** accesible desde el progreso o navegación secundaria; muestra minutos enfocados, sesiones completadas, tareas terminadas y lista de pendientes. Incluye estado vacío si aún no hay actividad.
Mantén un flujo vertical corto: Hoy → Nueva tarea → Sesión → Success → Hoy. La navegación inferior puede tener Hoy activo y Resumen como segunda sección; no añadas secciones que no aporten al objetivo.

INTERACCIONES Y ESTADOS
Implementa crear, editar lo mínimo necesario, completar/descompletar, eliminar con confirmación y elegir tarea principal. El timer debe persistir su estado localmente durante recargas, actualizarse en tiempo real y soportar activo, pausado, cancelado y completado. Cada feature importante debe tener loading/skeleton, populated, empty, error/retry, submitting/disabled y success. Evita botones sin feedback. Usa toasts accesibles y aria-labels; confirma acciones destructivas. Si falla la red al guardar, conserva el borrador local y muestra retry sin perder datos.

RESPONSIVE Y NAVEGACIÓN MÓVIL
Diseña primero para 390 px y verifica el rango 375–430 px. Usa safe areas, scroll correcto, controles táctiles de 44–56 px, teclado usable, CTA inferior fijo sin tapar contenido y bottom sheets que respeten el gesto de cierre. En anchos mayores amplía el lienzo con max-width, sin convertirlo en dashboard desktop. Respeta prefers-reduced-motion.

COMPONENTES Y STACK DIBOT
Conserva React + Vite + TypeScript + Bun + Tailwind, Base UI, Motion, Embla si hace falta, Phosphor Icons, React Router, Zustand, TanStack Query, React Hook Form, Zod, Drizzle ORM, `@libsql/client` y Turso/libSQL. No agregues otra UI framework ni reemplaces la arquitectura. Crea tokens semánticos para fondo, superficies, texto, primary, accent, estados, spacing y radios. Componentiza AppShell, TodayHeader, ProgressCard, FocusTaskCard, TaskRow, TaskComposer, FocusTimer, BottomNav, BottomSheet, Toast y EmptyState; mantén nombres y estilos coherentes.

API Y DATOS
Usa TanStack Query para todo remoto y Zustand solo para estado local de UI/timer/borrador. Como hay persistencia real, define Drizzle + Turso en `api/db/schema.ts` y todas las rutas server-side dentro de `api/`; jamás expongas secretos ni uses `VITE_` para credenciales. Modela al menos tasks (id, title, isPrimary, completed, createdAt, completedAt) y focusSessions (id, taskId, durationSeconds, startedAt, completedAt, status). Implementa endpoints para listar tareas del día, crear, completar y eliminar, más crear/terminar sesiones; valida payloads con Zod. Usa `TURSO_DATABASE_URL` y `TURSO_AUTH_TOKEN`, verifica `TURSO_DATABASE_ID` si reutilizas una base y ejecuta `bun run db:push` después del schema. No inventes persistencia en memoria como sustituto.

IMAGE PLAN
No uses imágenes reales en este MVP: el producto mejora con tipografía, formas y progreso, no con fotografía. Usa iconografía Phosphor y superficies CSS. No descargues ni reutilices assets de Mobbin, marcas o apps de terceros.

CRITERIOS DE ACEPTACIÓN Y VALIDACIÓN
- En 390 px se entiende Hoy en menos de cinco segundos y la tarea principal es la acción dominante.
- Se pueden crear, completar y eliminar tareas y los cambios sobreviven a recarga mediante Turso.
- El timer inicia en 25:00, cuenta correctamente, pausa/reanuda, cancela y registra success.
- Progreso y resumen reflejan el estado real; loading, empty, error, submitting y success están diseñados.
- Navegación, teclado, safe areas, foco, contraste y targets táctiles son usables.
- No hay secretos en cliente, errores TypeScript ni componentes sin feedback.
- Valida con `bun run build`; no sustituyas el stack ni dejes TODOs críticos.
